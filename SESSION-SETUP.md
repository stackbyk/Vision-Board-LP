# Workshop session setup

The booking API uses the existing `slot_label`, `slot_datetime`, `payment_status`, `consent`, and `created_at` columns. Run `migrations/20261027_bookings_rls.sql` in the Supabase SQL Editor before deploying. The earlier `20261027_booking_session.sql` migration is obsolete and is not required.

The session is configured in `SESSION_SLOTS` at the top of `payment.js`. Keep the server's `SELECTED_SLOT` in `api/create-order.js` aligned with it. The modal renders cards from the array; adding selectable sessions later will also require selection handling and a server allowlist.

The browser generates the booking UUID with `crypto.randomUUID()` and submits the hidden session value. `bookings.id` must accept UUIDs (not an integer identity). The single `/api/create-order` call runs the booking INSERT (without SELECT) and Razorpay order creation in parallel with `Promise.all`. Supabase and Razorpay clients are reused across warm server requests. The booking has `slot_label = "31 Oct 2026, 11:30 AM IST"`, `slot_datetime = "2026-10-31T11:30:00+05:30"`, consent true, and payment status pending. Its UUID is bound to Razorpay order notes. Payment verification checks the signature and order's booking ID, then updates `payment_status` to `paid` on that same row by `id`. It never inserts a second booking.

Reapply the updated RLS migration if an earlier version was already applied: inserts now permit an explicit `id` and require consent true. The database default supplies `created_at`. No live schema conversion or RLS change was performed. Because the operations run in parallel, a failed attempt can leave a pending booking or unused unpaid Razorpay order; checkout opens only if both succeed. Double clicks are blocked before async validation. Cancelling checkout reopens the dialog with the original details and country preserved.

Supabase access stays on the server using `SUPABASE_SERVICE_ROLE_KEY`; this key must never be placed in HTML or browser JavaScript. No Supabase key is needed by this frontend. If a direct browser client is added later, use only the public anon key and INSERT without `.select()`: public SELECT, UPDATE, and DELETE are deliberately denied. The server returns the new booking ID without exposing other attendees' records. The SQL also denies authenticated clients these operations; server/admin access remains available. Inspect existing application access needs before applying it if this table serves other clients.

There is no confirmation-email sender or spreadsheet/CRM integration in this repository. Configure the external workflow to include `bookings.slot_label` and `bookings.slot_datetime` in the confirmation email and spreadsheet/CRM mapping. No live database migration, payment, email, or CRM write was performed during local verification.
